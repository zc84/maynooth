# ERC-BROKENSONG — план реализации цифрового научного издания

Дата: 15 октября 2026 года.

Статус: первоначальный план для Discovery и последующей реализации.

Репозиторий: `https://github.com/zc84/maynooth`.

Рабочая директория: `/Users/dondimon/git/maynooth`.

## 1. Цель и исходное состояние

Создать публичное цифровое научное издание исследовательского проекта ERC-BROKENSONG о многоголосной музыке средневековой Британии и Ирландии приблизительно 1150–1350 годов. Платформа должна объединить каталог, изображения первоисточников, музыкальные транскрипции и исследовательские публикации, сохраняя различие между историческим свидетельством и редакторской интерпретацией.

Ориентир объёма: около 130 рукописных источников и более 700 музыкальных композиций. Это масштаб коллекции из задания, а не подтверждённое количество подготовленных к публикации записей. Число рукописных свидетельств, изображений и редакций необходимо определить отдельно.

На момент подготовки плана репозиторий содержит:

- `index.html` — англоязычный статический концепт главной страницы;
- `styles.css` — адаптивные стили, палитру и типографические решения;
- `assets/folio.svg`, `assets/monogram.svg`, `assets/notation.svg` — иллюстрации и монограмму;
- `README.md` — описание концепта и запуск без сборки.

Каталог, модели научных данных, поисковый индекс, JavaScript-приложение, MEI/IIIF-интеграции и автоматическая публикация пока отсутствуют. Существующий дизайн — отправная точка для обсуждения визуальной идентичности, а не утверждённый дизайн всей платформы. В частности, текущую надпись `100+` источников следует заменить статистикой опубликованного корпуса; иллюстрацию фолио нельзя выдавать за реальный источник.

## 2. Результат первого публичного релиза

Первый релиз должен представлять собой завершённое издание с согласованным корпусом данных, а не только демонстрационную главную страницу.

| Направление | Обязательный результат |
| --- | --- |
| Идентичность | Утверждённые логотип, палитра, типографика, правила изображений и краткое руководство по стилю |
| Главная | Описание проекта, статистика опубликованной коллекции, избранные источники, новости и публикации |
| Каталоги | Отдельные каталоги источников и композиций, связанные общей моделью данных |
| Поиск | Текстовый поиск, комбинируемые фильтры, сортировка, постоянная ссылка на состояние выдачи |
| Источник | Метаданные, листы/фрагменты, изображения, связанные композиции, библиография и права |
| Композиция | Метаданные, рукописные свидетельства, редакции, MEI-партитура и научный комментарий |
| Рабочая область | IIIF-просмотр, Verovio, режим «изображение + партитура» и переключение режимов на мобильном устройстве |
| Научная прозрачность | Явные статусы сохранности, маркировка реконструкций, авторство и версия редакции |
| Редакционный процесс | Проверяемый импорт, предварительный просмотр, научное утверждение и воспроизводимая публикация |
| Эксплуатация | Развёртывание, откат, резервирование, документация, обучение и назначенный владелец сопровождения |

В базовый объём не включать пользовательские аккаунты, публичное редактирование, социальные функции, поиск по музыкальному мотиву, автоматическое распознавание нот, полную оцифровку рукописей и создание всего MEI-корпуса с нуля. Подготовка и научная редактура материалов — отдельный поток работ команды исследователей. Воспроизведение звука, синхронизация нота за нотой, карты и расширенная аналитика — возможное развитие после базового релиза. Простую привязку партитуры к листу включить в первый релиз там, где предоставлены соответствующие данные.

## 3. Discovery: что выяснить до фиксации архитектуры

Провести рабочие сессии с руководителем проекта, музыковедами, редакторами данных, библиотечными/архивными специалистами и ответственным за университетскую инфраструктуру.

| Вопрос | Что получить | Как влияет на реализацию |
| --- | --- | --- |
| Исходные данные | Образцы выгрузок, схема, справочники, доля заполнения, перечень владельцев полей | Определяет импорт, обязательные поля и объём очистки |
| Существующая инфраструктура | Документация API, примеры ответов, доступы, лимиты, лицензии и процесс обновления | Позволяет выбрать интеграцию вместо создания дублирующей базы |
| Научная модель | Определения произведения, свидетельства, фрагмента, версии и реконструкции | Предотвращает смешение разных объектов в каталоге |
| MEI | Реальные файлы, версия схемы, типы нотации, редакционные элементы, сложные случаи | Определяет совместимость Verovio и правила отображения |
| Изображения | IIIF manifests, canvases, Image API, HTTPS/CORS, права и ограничения доступа | Определяет доступные изображения и необходимость собственного сервиса |
| DIAMM | Идентификаторы, разрешённые ссылки, подтверждённые интерфейсы и условия использования | Определяет глубину интеграции; наличие пригодного API не предполагается |
| Редактирование | Кто обновляет данные, частота, знакомство с Git, необходимость браузерного интерфейса | Определяет основной редакционный инструмент |
| Аудитории | Задачи исследователей, исполнителей, студентов и широкой публики | Определяет навигацию и глубину пояснений |
| Языки | Язык интерфейса, языки публикаций, оригинальных текстов и переводов | Предварительно: интерфейс на английском, многоязычные данные с самого начала |
| Институциональные требования | Домен, брендинг ERC/университета, хостинг, доступность, аналитика, архивирование | Определяет ограничения дизайна и размещения |
| Сроки и бюджет | Дата релиза, доступность команды, бюджет разработки и ежегодной эксплуатации | Позволяет утвердить реалистичный объём |

Получить репрезентативный пилот: ориентировочно 10–15 источников и 30–50 композиций, включая несколько свидетельств одного произведения, неполные голоса, неопределённую датировку, реконструкцию, несколько редакций, многоязычный текст и отсутствующее изображение. По возможности включить IIIF Presentation 2 и 3, несколько поставщиков изображений и все реально используемые типы MEI.

Результаты Discovery: реестр требований, словарь данных, карта существующих систем, матрица прав, список рисков, редакционный процесс, план миграции и уточнённые оценки. Выбор стека зафиксировать в архитектурном решении после технического прототипа.

### 3.1. Роль архитектора / технического лида

На P0–P2 назначить ответственного за архитектуру с опытом интеграций, моделирования данных и публикации исследовательских материалов. Роль может выполнять один из двух разработчиков в качестве технического лида; отдельная постоянная ставка архитектора не является исходным требованием. Его архитектурные задачи должны быть учтены в загрузке и оценке, а технический владелец со стороны университета обеспечивает институциональные решения и дальнейшее сопровождение.

Зона ответственности технического лида:

- согласовать с научным редактором модель произведений, свидетельств и редакций, стабильные ID и правила сопоставления внешних записей;
- определить источник истины для каждого набора данных, контракты адаптеров, обновление снимков, валидацию, кэширование и поведение при отказах;
- разделить поиск по метаданным, загрузку медиа и возможный поиск по музыкальному содержанию; обосновать необходимость серверных компонентов;
- проверить связку Mirador–Verovio–MEI–IIIF на реальных материалах, включая совместный просмотр, реконструкции, мобильный режим и доступность;
- подготовить архитектурное решение, границы модулей, распределение работ и уточнённую оценку разработки и эксплуатации.

### 3.2. Контрольная точка после технического прототипа

До начала основной реализации P3 технический лид выпускает отчёт P2: проверенные источники и права, схема связей, поддерживаемый профиль MEI, результаты интеграций, измерения поискового индекса и viewer, нерешённые ограничения и варианты архитектуры с оценкой стоимости. В отчёте должны быть отдельно видны объём импорта/серверной обработки и объём фронтенд-интеграций.

Сложность бэкенда и потребность в отдельном специалисте оцениваются по этому отчёту. Количество интеграций и размер изображений сами по себе не определяют необходимость постоянно работающего сервера. Если нужны дополнительная база, серверный поиск, CMS, собственная доставка изображений или обработка защищённых ресурсов, их задачи, трудоёмкость и расходы включаются в уточнённый план до P3.

## 4. Информационная архитектура и основные сценарии

Предлагаемые разделы и адреса:

| Адрес | Содержание |
| --- | --- |
| `/` | Главная и входы в коллекцию |
| `/manuscripts/` | Каталог источников |
| `/manuscripts/{id}/` | Источник, физические фрагменты/листы, изображения и состав |
| `/compositions/` | Каталог композиций |
| `/compositions/{id}/` | Произведение, свидетельства, редакции и партитура |
| `/search/` | Поиск по каталогу и опубликованным материалам |
| `/publications/`, `/publications/{slug}/` | Научные публикации и библиографические записи |
| `/news/`, `/news/{slug}/` | Новости проекта |
| `/about/`, `/team/`, `/methodology/` | Проект, команда и принципы издания |
| `/help/`, `/accessibility/`, `/rights/` | Помощь, доступность, правила использования материалов |
| `/data/` | Описание схемы, версии и разрешённые открытые выгрузки |

Идентификатор научного объекта стабилен и не зависит от названия или библиотечного шифра. Читаемый slug допустим как дополнение; при изменении адреса создаётся перенаправление. Внутренние связи строятся по ID.

Приоритетные сценарии:

1. Найти композиции по инципиту, языку, жанру, датировке и числу голосов; открыть произведение, выбрать свидетельство и редакцию.
2. Найти источник по шифру, учреждению, месту хранения или типу нотации; просмотреть лист и перейти к связанному произведению.
3. Открыть изображение и партитуру рядом; выбрать нужный лист по подготовленной привязке; понять, какие участки реконструированы.
4. Скопировать ссылку на объект, редакцию и выбранный лист, получить корректную библиографическую ссылку и разрешённый MEI-файл.
5. Прочитать исследовательскую публикацию и перейти к упомянутым источникам и композициям.
6. Редактор обновляет данные, проверяет результат в preview и публикует после научного утверждения.

## 5. Модель данных и научные правила

### 5.1. Сущности

| Сущность | Назначение и ключевые поля |
| --- | --- |
| Manuscript / Source | ID, шифр, альтернативные шифры, учреждение, местонахождение, датировка, происхождение, описание, библиография, внешние ID, права |
| Fragment / Folio | ID, sourceId, физическое обозначение, порядок, recto/verso, сохранность, manifest URL, canvas ID, при необходимости область изображения |
| Composition / Work | ID, предпочтительное название/инципит, альтернативные названия, текст, языки, жанры, предполагаемое авторство, датировка, научный комментарий |
| Witness | ID, compositionId, sourceId, ссылки на фрагменты/листы, порядок в источнике, нотация, засвидетельствованные голоса, лакуны, состояние сохранности |
| Edition | ID, compositionId, связанные witness IDs, тип редакции, редактор, дата, версия, MEI, права, editorial statement и статус публикации |
| Facsimile mapping | editionId, MEI xml:id/диапазон, witnessId, canvas ID, при наличии координаты области; используется только при подтверждённой привязке |
| Publication | ID, название, авторы, дата, тип, библиографическая ссылка, DOI/URL, аннотация, связанные научные объекты, права |
| News / Page | Заголовок, дата, содержание, автор, связанные объекты, статус публикации |
| Authority / Vocabulary | Учреждения, лица, места, языки, жанры, нотации, статусы; стабильные ID и отображаемые подписи |

Основная связь: одно произведение имеет несколько рукописных свидетельств; один источник содержит несколько свидетельств. Редакция может опираться на одно или несколько свидетельств. Количество композиций и количество свидетельств считаются отдельно. Для разрозненных фрагментов одного исторического кодекса предусмотреть связь с реконструированным кодексом без потери отдельных современных шифров и мест хранения.

### 5.2. Датировки, неопределённость и сохранность

- Сохранять исходную формулировку датировки и отдельные нормализованные границы `dateFrom` / `dateTo`; дополнительно — уверенность, основание и источник атрибуции. Не подменять неизвестную дату нулём.
- Различать дату создания источника, предполагаемую дату сочинения и дату современной редакции. Фильтры явно указывают, какое поле используется.
- Не ограничивать импорт жёстко 1150–1350 годами: это исследовательский фокус, а границы отдельных датировок могут выходить за него.
- Число сохранившихся голосов и предполагаемое полное число голосов хранить раздельно; неопределённое значение не считать нулём.
- Разделять физическую сохранность источника, полноту конкретного свидетельства и тип редакции: «транскрипция», «реконструкция», «смешанная».
- Для спорных авторских атрибуций, жанров и происхождения хранить квалификаторы и библиографические основания. Справочники поддерживают несколько значений.

### 5.3. Реконструкции и MEI

Утвердить совместно с музыковедами профиль MEI: используемую схему, правила кодирования лакун, дополнений, спорных чтений и ответственных редакторов. Конкретное применение элементов, например `gap`, `supplied`, `unclear`, `app` / `rdg`, проверить на реальном корпусе и выбранной версии Verovio.

Каждая опубликованная редакция содержит авторство, дату/версию, основание реконструкции и список использованных свидетельств. В интерфейсе тип редакции виден до открытия партитуры. Реконструированные фрагменты различаются текстовой легендой и графическим приёмом; цвет не служит единственным обозначением. Маркировка сохраняется при скачивании материалов либо сопровождается явным описанием в метаданных и документации.

Если данных для привязки нот к изображению нет, показывать совместный просмотр без обещания автоматической синхронизации. Версия MEI, не поддерживаемая рендерером, не должна автоматически преобразовываться с потерей исходной научной информации: оригинал сохраняется, производные файлы создаются отдельно.

### 5.4. Контроль качества и публикация

Минимальные поля публикуемой записи: стабильный ID, тип, название или шифр, статус, происхождение записи, решение о правах и необходимые связи. Отсутствие изображения или MEI допустимо, если это явно обозначено; оно не должно исключать научно значимую каталожную запись.

Проверять уникальность ID, целостность ссылок, справочники, диапазоны дат, допустимые URL, версию схемы, XML/MEI и наличие прав для конкретного способа публикации. Синтаксическая проверка MEI не заменяет научную редактуру. Отчёт разделяет ошибки, блокирующие публикацию, и предупреждения о неполных данных. Черновики и закрытые материалы исключаются из HTML, JSON, индекса и скачиваемых архивов.

## 6. Рекомендуемая техническая архитектура

### 6.1. Базовое решение

Предварительный выбор — Astro + TypeScript со статической генерацией страниц, небольшими интерактивными модулями и размещением готовой сборки на CDN либо университетском статическом хостинге. React использовать для интеграции Mirador и, при необходимости, других сложных компонентов. Astro поддерживает разделение статического HTML и интерактивных компонентов: [Islands architecture](https://docs.astro.build/en/concepts/islands/).

Рекомендация обусловлена предполагаемым объёмом корпуса и требованием низких эксплуатационных расходов. Она подлежит проверке на полном наборе метаданных и сложных MEI. Номера библиотек и runtime фиксировать в lockfile и CI после прототипа совместимости, без зависимостей от плавающего `latest` в production.

| Слой | Предлагаемый подход |
| --- | --- |
| Публичные страницы | Предварительно сгенерированные HTML; метаданные доступны без загрузки viewer |
| Данные каталога | Версионируемый нормализованный JSON с проверяемой схемой |
| Публикации и новости | Markdown с метаданными или экспорт существующего редакционного инструмента |
| Поиск и фильтры | Локальный индекс опубликованных метаданных; точный выбор библиотеки после измерения размера и качества поиска |
| IIIF | Mirador как изолированный модуль, загружаемый при открытии просмотра |
| Партитура | Verovio WebAssembly, SVG и загрузка MEI по запросу; тяжёлый рендеринг по возможности в Web Worker |
| Интеграции | Адаптеры импорта из подтверждённых API/выгрузок; браузер получает только публичные ресурсы |
| Публикация | CI: импорт → валидация → генерация страниц и индекса → проверки → preview → выпуск |
| Хостинг | CDN/статический хостинг с HTTPS, собственным доменом, preview и откатом |

Публичный сайт читает согласованный снимок данных. Сбой исходного API не должен ломать уже опубликованное издание. Обновление снимка запускается вручную или подтверждённым событием из системы-источника; при ошибке импорта остаётся предыдущая опубликованная версия. Фиксировать источник, время получения, контрольную сумму и идентификатор релиза.

Не смешивать обязанности систем: если у проекта уже есть основная база, она остаётся источником истины для закреплённых за ней полей. Ручные дополнения сайта хранятся отдельно и объединяются по ID; конфликты формируют отчёт. Если основной базы нет, нормализованные файлы с редакционным процессом становятся первым источником истины.

### 6.2. Условия изменения архитектуры

- Если редакторам необходим браузерный интерфейс, использовать пригодную существующую CMS или добавить управляемый редакционный инструмент. Это отдельное решение Discovery с оценкой стоимости, доступа и резервирования.
- Если обязательны персональные рабочие пространства, приватный контент или публикация без пересборки, оценить серверную часть. Эти функции меняют базовый объём.
- Если индекс и время обработки не укладываются в согласованные бюджеты на целевых устройствах, вынести поиск в управляемый сервис или университетскую инфраструктуру. Сначала измерить, затем усложнять.
- Если поставщики не предоставляют пригодный IIIF, отдельно оценить подготовку тайлов и manifest, хранение, трафик, права и обслуживание. JSON manifest сам по себе не создаёт Image API.

### 6.3. Предлагаемая структура после начала разработки

```text
src/
  pages/                 # Страницы и генерируемые публичные JSON-ресурсы
  layouts/               # Общие шаблоны

  viewers/               # Обёртки Mirador, Verovio и общая рабочая область
```

Закрытые исходники и секреты не помещать в `public/` или публичный репозиторий. Для крупных MEI-корпусов, изображений и архивов выбрать подходящее объектное/институциональное хранилище; Git хранит код, схемы, небольшие метаданные и разрешённые образцы. Путь размещения файлов не должен менять стабильные адреса научных объектов.

## 7. Проработка функциональных модулей

### 7.1. Визуальная идентичность и интерфейс

Оценить существующую концепцию: бумажные фоны, тёмные чернила, красные редакционные акценты, сочетание антиквы и гротеска. Проверить читаемость плотных таблиц, контраст текущего приглушённого текста и навигации, масштабирование шрифтов и уместность декоративных элементов в научной рабочей области.

Подготовить 1–2 направления и развить выбранное в дизайн-систему: логотип и монохромный вариант, favicon, цветовые и типографические токены, сетка, навигация, поля, фильтры, карточки, таблицы, пагинация, вкладки, статусы, загрузка, пустые состояния и ошибки. Проверить поддержку средневековых текстов, диакритики и музыкальных знаков; согласовать лицензии шрифтов и возможность локального размещения.

Спроектировать главную, оба каталога, обе детальные страницы, совместный просмотр, публикацию и служебные страницы для мобильного и настольного экранов. Подготовить английские UI-тексты и объяснения научных терминов. Согласовать размещение институциональных знаков и funding acknowledgement. Финальные материалы: исходники логотипа, SVG/PNG-экспорты, токены и краткое руководство.

### 7.2. Главная и публикационные разделы

Статистику вычислять из опубликованного снимка, подписывая единицы: источники, композиции, свидетельства, доступные редакции. Не подменять целевые размеры коллекции количеством реально опубликованных материалов. Избранные источники и порядок блоков управляются редакционными данными. Новости и публикации имеют отдельные списки и страницы; внешняя публикация может иметь только метаданные и ссылку, если полный текст недоступен для размещения.

### 7.3. Поиск, сортировка и фильтры

В первом релизе поиск работает по нормализованному локальному снимку опубликованных метаданных и согласованному объёму текстов. Каждый пользовательский запрос не должен зависеть от одновременного ответа DIAMM и других внешних систем. Во время импорта разрешённые поисковые поля извлекаются и связываются по ID; бинарные изображения и полные MEI не загружаются для выполнения обычного каталожного запроса.

| Задача | Реализация / граница объёма |
| --- | --- |
| Поиск по шифрам, инципитам, датам, языкам, жанрам и голосам | Базовый объём; локальный индекс и проверенные правила фильтрации |
| Получение изображения или рендеринг партитуры | Отдельный контур просмотра с загрузкой по запросу; измерять независимо от поиска |
| Поиск по нотным последовательностям, мелодическим мотивам или распознанному содержимому изображений | Расширение с отдельной исследовательской и технической оценкой |

Около 130 источников и 700+ композиций — исходный ориентир для прототипа локального поиска, а не доказательство его достаточности: фактический индекс зависит также от числа свидетельств, длины текстов и связей. Решение о серверном поиске принимается по качеству результатов, размеру индекса и скорости на целевых устройствах согласно разделу 9.2.

- Искать по названию, инципиту, альтернативным написаниям, шифрам, учреждениям и доступному текстовому описанию; публикации включить отдельным типом результата.
- Согласовать нормализацию регистра, пробелов, пунктуации и диакритики. Исторические варианты и соответствия `u/v`, `i/j` вводить как контролируемые правила/алиасы, а не безусловную замену.
- Фильтры источников: датировка, учреждение/местонахождение, происхождение, тип нотации, сохранность, наличие изображений. Язык, жанр и голоса при фильтрации источников берутся из явно определённых связанных свидетельств.
- Фильтры композиций: датировка, жанр, язык, число голосов, нотация, источник, полнота свидетельства, наличие MEI и тип редакции. Поля нотации и сохранности относятся к свидетельствам и отображаются с этим пояснением.
- По разным группам фильтров применять AND, внутри многозначной группы — OR. Если несколько условий относятся к свидетельству, они должны выполняться у одного и того же свидетельства; не объединять случайно язык из одной записи и число голосов из другой.
- Даты сопоставлять по пересечению интервалов; неизвестные даты доступны отдельным значением. Для голоса указывать, используется ли сохранившееся или предполагаемое число.
- Сортировки: релевантность при запросе, название/шифр, датировка, дата обновления. Указать порядок неизвестных дат и вторичный стабильный ключ ID.
- Состояние запроса, фильтров, сортировки и страницы хранить в URL; поддержать Back/Forward, очистку фильтров, счётчики и доступное уведомление о числе результатов.
- Ограничить выдачу пагинацией; не создавать бесконечные индексируемые комбинации URL. Метаданные объектов и ссылки на них доступны в обычном HTML; интерактивный поиск использует JavaScript.

На пилоте подготовить согласованный набор запросов с ожидаемыми результатами. Полнотекстовый поиск по всем научным публикациям включается в согласованном объёме текстов; поиск по изображениям и музыкальному содержанию MEI в этот модуль не входит.

### 7.4. Просмотр рукописей и интеграция IIIF

Mirador — предварительно выбранный IIIF viewer; официальный сайт заявляет поддержку Image и Presentation API v2/v3: [Mirador](https://projectmirador.org/). Совместимость выбранной сборки проверить на реальных manifests, а не только на демонстрационных данных.

Реализовать масштабирование, перемещение, выбор листа, миниатюры, полноэкранный режим, подписи, обязательную атрибуцию и ссылку на учреждение-держатель. Использовать устойчивый canvas ID, а не только порядковый номер страницы. Сохранять выбранный лист в URL. Ограниченные коллекции не обходить; при невозможности публичного показа оставлять метаданные и разрешённую ссылку на поставщика.

Проверить HTTPS, CORS, нужные заголовки, лимиты, перенаправления и фактическое разрешение изображения. Сбой manifest или Image API показывает понятное состояние и внешнюю ссылку, не блокируя всю карточку. При отсутствии IIIF статическая иллюстрация допускается только с разрешением и честной подписью об ограниченном просмотре.

### 7.5. Музыкальная нотация и совместный просмотр

Проверить на пилоте чтение MEI, постраничный SVG, изменение масштаба/ширины и редакционную маркировку. Официальный toolkit предоставляет браузерную WebAssembly-сборку: [Verovio JavaScript and WebAssembly](https://book.verovio.org/installing-or-building-from-sources/javascript-and-webassembly.html).

Загружать toolkit и MEI при открытии партитуры, обрабатывать некорректный файл и отсутствие поддерживаемой нотации. Для больших файлов проверить Web Worker, последовательный рендеринг страниц и ограниченный кэш; при сложных случаях предусмотреть подготовленный статический SVG, явно связанный с версией MEI. Проверить перенос `xml:id` в SVG на реальных файлах перед использованием для подсветки и навигации.

На широком экране дать две регулируемые панели; на узком — вкладки «Рукопись» / «Партитура» с сохранением выбранного свидетельства, редакции и листа. Переключение между разными свидетельствами не должно незаметно оставлять партитуру, относящуюся к другому источнику: связь и основание редакции видны пользователю.

В первом релизе синхронизация означает выбор связанного листа/раздела по подготовленной карте. Подсветка отдельных музыкальных событий возможна только при наличии проверенных координат и идентификаторов и оценивается отдельно.

Оценивать фронтенд-интеграцию как самостоятельный пакет P5: общий контроллер выбранного произведения/свидетельства/редакции/canvas, адаптеры двух viewers, согласованное состояние в URL, отмена устаревших загрузок при переключении, освобождение ресурсов, независимые ошибки и клавиатурное управление. При повторном переключении поздний ответ предыдущего запроса не должен подменять выбранное пользователем изображение или партитуру. Эти работы входят в оценку даже при статическом размещении сайта.

### 7.6. Внешние системы и открытые данные

Для каждой интеграции документировать владельца, URL, версию/контракт, права, ограничения, обязательные атрибуции, способ авторизации и поведение при недоступности. Секреты API используются только при импорте в защищённой среде.

DIAMM, MEI files + metadata и IIIF manifests + images — три направления интеграционной проверки, а не три заранее подтверждённых независимых API. MEI является форматом музыкальных файлов; IIIF задаёт интерфейсы представления и доставки ресурсов; фактических поставщиков, общие идентификаторы и пересечения данных необходимо установить в P0–P2.

| Направление | Импорт / обработка данных | Работа в браузере | Что подтвердить на P2 |
| --- | --- | --- | --- |
| DIAMM и существующий API проекта | При наличии разрешённого интерфейса — получение метаданных, сопоставление ID, обновление снимка | Каталожные сведения из снимка и проверенные внешние ссылки | Доступность и условия интерфейса, схема, лимиты, права; для DIAMM допустим базовый вариант только со ссылками |
| MEI files + metadata | Проверка XML/MEI, версии, прав, редакционных признаков и связей; подготовка разрешённых файлов | Загрузка выбранного MEI, рендеринг Verovio, выбор редакции и легенда реконструкций | Поддерживаемая нотация, сохранение научных различий, время и память рендера |
| IIIF manifests + images | Проверка ссылок, структуры manifest, canvas ID, атрибуции и соответствия листам | Mirador получает разрешённые manifests и изображения от поставщика | HTTPS/CORS, доступ к тайлам, устойчивость canvas ID, права и поведение при сбое |

Для всех направлений обязательна проверка соответствия одной и той же научной записи: произведение → свидетельство → лист/canvas → редакция. Недоступность API импорта блокирует обновление снимка, а недоступность изображения или MEI показывает локальную ошибку просмотра при сохранении карточки и остальных доступных материалов.

Для DIAMM базовый результат — проверенные внешние ссылки и идентификаторы на соответствующих карточках. Автоматический импорт и показ ресурсов добавляются при подтверждении подходящего интерфейса и разрешений; не строить критическую функцию на недокументированном scraping. Аналогично обрабатывать DOI и другие внешние справочники.

Предусмотреть публичные статические JSON-выгрузки с версией схемы и релиза; CSV — для согласованного плоского представления. Полноценный динамический REST/GraphQL API не требуется для базового сайта и может быть отдельным расширением. Для данных, изображений, MEI и статей указывать собственные лицензии; открытый доступ к странице не означает права на повторную публикацию всех её материалов.

## 8. Редакционный процесс и миграция

Основной процесс: получение исходных данных → нормализация → автоматическая проверка → редакторская проверка → научное утверждение → preview → публикация релиза. Отдельно назначить того, кто принимает научные решения, и того, кто технически выпускает сайт; один человек может совмещать роли при явном согласовании.

1. Инвентаризировать все записи и файлы, зафиксировать количество, формат, права и качество.
2. Составить таблицу соответствия полей и ID, определить правила дубликатов и приоритет источников.
3. Выполнить пилотный импорт; получить отчёт преобразований, потерь, предупреждений и конфликтов.
4. Реализовать повторяемый импорт без создания дубликатов, с режимом проверки без публикации и понятным журналом.
5. Утвердить пилот у научной команды и только затем переносить полный корпус.
6. Сверить исходные и итоговые количества по типам, связи, выборку сложных записей и все обнаруженные исключения.
7. Заморозить согласованный набор для релиза, собрать версионированный снимок и сохранить исходники в разрешённом хранилище.

Отчёт должен различать ошибочную потерю записи и сознательное исключение черновика/материала без прав. Массовые исправления исходного научного содержания выполняются только по согласованным правилам с фиксацией происхождения.

Основной инструмент редактирования выбирается в Discovery: существующая система, файлы с помощью подготовленных шаблонов или браузерный редактор. Если выбран файловый процесс, обучение должно подтвердить, что назначенные редакторы способны им пользоваться; иначе нужен другой инструмент. Каждая публикация фиксирует версию данных и дату; ошибка в обновлении не меняет опубликованный релиз до успешных проверок.

## 9. Доступность, производительность и безопасность

### 9.1. Доступность

Цель — WCAG 2.2 AA для публичных сценариев; проверять собственный интерфейс и интегрированные viewers: [WCAG 2.2](https://www.w3.org/TR/WCAG22/). Автоматический отчёт не является доказательством полного соответствия.

Обязательны семантическая структура, клавиатурная навигация, видимый фокус, корректные названия элементов, skip-link, контраст, доступные ошибки, изменение масштаба до 200–400%, отсутствие блокирующих focus traps и поддержка reduced motion. Плотные таблицы и двухпанельный просмотр должны оставаться управляемыми на узком экране.

Для музыкального SVG и изображений предусмотреть текстовый инципит, метаданные, описание сохранности, редакционный комментарий, пояснение легенды и разрешённые исходные файлы. Само наличие SVG или MEI не делает партитуру доступной для скринридера. Определить с командой пригодное текстовое представление; документировать и приоритизировать ограничения сторонних viewers. Внешняя ссылка не заменяет устранение критического барьера в обязательном сценарии.

### 9.2. Производительность

Предварительные бюджеты, уточняемые по пилоту:

- Обычная страница каталога/объекта: LCP ≤ 2,5 с, CLS ≤ 0,1; после запуска при достаточной полевой выборке — INP ≤ 200 мс на 75-м перцентиле. До запуска использовать воспроизводимые лабораторные измерения и сценарии взаимодействия.
- Первая загрузка обычной страницы не включает Mirador, Verovio и полный MEI-корпус; ориентир начального JavaScript страницы без viewer — до 150 КБ gzip.
- Поисковые метаданные: ориентир до 1 МБ gzip и обработка типового фильтра ≤ 200 мс на согласованном устройстве после загрузки индекса. Точные условия и состав корпуса записать в отчёте.
- Viewer показывает состояние загрузки сразу; время получения изображения и рендера измеряется отдельно с учётом поставщика, сети, размера MEI и холодного запуска WebAssembly.
- Использовать адаптивные изображения/тайлы, кэшируемые версионированные ресурсы, локальные шрифты при подходящей лицензии и ограничение фоновых запросов.

Это инженерные цели, а не уже достигнутые показатели. Если крупный корпус требует пересмотра индекса или viewer, решение принимается по измерениям до релиза.

### 9.3. Безопасность и права

Ограничить обрабатываемые URL доверенными протоколами и согласованными источниками; для автоматического импорта исключить обращения к локальной/внутренней сети через подставленные адреса и перенаправления. Проверять и безопасно выводить импортируемые HTML, XML и SVG; отключать внешние XML-сущности в инструментах разбора. Не публиковать секреты, черновики и закрытые изображения.

Настроить HTTPS, минимальные права CI, проверку зависимостей и CSP, совместимую с реально используемыми IIIF-доменами, WebAssembly и workers. Политику CSP проверить на staging. Аналитика и сторонние сервисы подключаются после институционального решения о приватности и необходимости согласий.

## 10. Этапы, зависимости и критерии завершения

Оценка календаря: ориентировочно 14–18 недель при участии двух разработчиков, один из которых выполняет роль технического лида/архитектора, дизайнера на части этапов, QA/специалиста по доступности и регулярно доступного научного редактора. Один разработчик либо неполный корпус увеличат срок. Этапы частично перекрываются; это плановая оценка, не обязательство по дате. Трудоёмкость и стоимость уточняются после Discovery и контрольной точки P2; архитектурная работа входит в загрузку команды.

Предварительное распределение: технический лид ведёт P0/P2, модель данных, импорт и CI; второй разработчик — UI, поиск и рабочую область с Mirador/Verovio. Решения по научной семантике утверждает научный редактор, технический владелец университета отвечает за инфраструктуру и передачу в сопровождение. Если P2 выявит значительный серверный контур, отдельно пересмотреть распределение, срок и необходимость backend/data engineer; текущая оценка не предполагает заранее разработку сложного бэкенда.

| Этап | Окно / длительность | Задачи и результат | Зависимость и критерий завершения |
| --- | --- | --- | --- |
| P0. Discovery | Недели 1–2 / 2 недели | Интервью, аудит данных/прав/API, пилотный корпус, границы релиза, реестр рисков | Научный руководитель и технический владелец согласовали требования, источники данных и открытые вопросы |
| P1. UX и идентичность | Недели 2–4 / 3 недели | Сценарии, структура сайта, логотип, токены, макеты основных экранов и состояний | После первичных выводов P0; пройдены разбор с исследователями и проверка ключевых сценариев |
| P2. Модель и технический прототип | Недели 3–5 / 3 недели | Схема Source–Witness–Work–Edition, импорт пилота, IIIF, MEI, двухпанельный просмотр и измерения поиска | Технический лид представил отчёт по разделу 3.2; подтверждены сложные MEI, редакционная маркировка, реальные manifests, архитектура и уточнённая оценка |

| P4. Каталоги и публикации | Недели 7–10 / 4 недели | Карточки, связи, поиск/фильтры, главная, новости, публикации, цитирование и выгрузки | P3; согласованные поисковые запросы дают ожидаемые результаты, черновики исключены |
| P5. Научная рабочая область | Недели 8–12 / 5 недель | Production-интеграции Mirador/Verovio, выбор редакций, маркировка, привязки к листам, мобильный режим, ошибки | Успешный P2 и карточки P4; проверены все обязательные случаи пилота и сценарии недоступности |

Критический путь: доступ к данным и правам → научная модель → успешный технический прототип → каталоги/viewers → готовность полного корпуса → приёмка → запуск. Визуальная работа и подготовка данных идут параллельно. Длительная ручная MEI-кодировка, согласование прав с учреждениями и разработка собственного IIIF-сервиса требуют отдельной оценки.

После каждого этапа обновлять этот план фактическими решениями и оставшимися рисками. Задачи разработки формировать по P0–P7 с владельцем, зависимостями, ожидаемым результатом и проверяемым критерием приёмки.

## 11. Стратегия тестирования и приёмка релиза

| Уровень | Что проверять | Условие приёмки |
| --- | --- | --- |
| Данные | ID, связи, справочники, права, даты, MEI, исключение черновиков, сверка импорта | Нет необъяснённых потерь и блокирующих ошибок; предупреждения рассмотрены редактором |
| Логика | Датировочные интервалы, неизвестные значения, witness-фильтры, сортировки, URL-состояние, статистика | Результаты соответствуют согласованным примерам и научной семантике |
| Интеграции | IIIF v2/v3, canvas, CORS, тайм-ауты, неверные ответы, разные MEI и WebAssembly | Поддерживаемые материалы открываются; сбои не уничтожают метаданные страницы |
| Пользовательские сценарии | Поиск → объект → свидетельство → совместный просмотр → цитирование/скачивание | Сценарии проходят на настольном и мобильном экранах, ссылки воспроизводят состояние |
| Доступность | Автоматическая проверка, клавиатура, скринридер, масштабирование и контраст | Нет критических барьеров; остальные ограничения и исправления документированы |
| Визуальное качество | Основные страницы, длинные шифры, сложные тексты, пустые и ошибочные состояния | Нет потери содержимого, перекрытий и неуправляемых элементов |
| Производительность | Полный индекс, холодный/повторный запуск viewer, крупный MEI, медленная сеть | Достигнуты согласованные бюджеты либо до релиза принято обоснованное решение об изменении реализации |
| Безопасность | Недоверенные метаданные/URL, XML/SVG, секреты, права, настройки production | Закрытые материалы отсутствуют в артефактах, опасное содержимое не исполняется |
| Научная UAT | Состав источника, редакции, лакуны, реконструкции, атрибуции, цитаты | Уполномоченный научный редактор утвердил корпус и репрезентативную выборку представления |
| Эксплуатация | Сборка из чистого checkout, публикация, откат, восстановление и обновление | Процедуры воспроизводимы ответственным сотрудником по документации |

Предварительная браузерная матрица: актуальные стабильные Chrome, Firefox, Safari, Edge; Safari на iOS и Chrome на Android. Точные версии и устройства зафиксировать при начале QA. Для доступности включить VoiceOver/Safari и NVDA/Firefox либо согласованные доступные эквиваленты.

Модульные и интеграционные тесты выбирать для научной логики, импорта и отказов; end-to-end — для критических пользовательских сценариев. Для повторяемых CI-проверок использовать разрешённые локальные fixtures, а живые внешние IIIF/API проверять отдельно, чтобы случайный сбой поставщика не делал тесты недостоверными.

Публичный запуск возможен, когда выполнены требования раздела 2, утверждён согласованный опубликованный корпус, отсутствуют дефекты с потерей данных, неверным научным представлением, нарушением прав или блокировкой основных сценариев и назначен владелец сопровождения. Если доступна только часть ожидаемых 130/700+ объектов, размер и статус релиза явно согласуются и отображаются на сайте; неполный корпус нельзя молча объявить полным изданием.

## 12. Развёртывание, стоимость и устойчивость

Выбрать размещение после проверки требований университета: предпочтителен существующий институциональный статический хостинг; альтернатива — управляемый CDN-хостинг. До выбора подтвердить домен, заголовки/CORS, WebAssembly MIME, лимиты сборок, артефактов и трафика, preview и откат. Бесплатные тарифы не считать гарантией бессрочной бесплатной эксплуатации.

Поддерживать локальную среду, staging/preview и production. В CI установить зависимости по lockfile, проверить данные, собрать сайт и индекс, выполнить необходимые проверки и сохранить неизменяемый артефакт. Preview закрыть от индексации; для неопубликованного контента требуется контроль доступа, одного `noindex` недостаточно. Production-выпуск выполнять из проверенного артефакта с тегом/ID релиза.

Перед запуском: проверить DNS/TLS, redirects, canonical, sitemap, robots, 404, социальные метаданные, доступность файлов и изображений, обязательную атрибуцию и ссылки. Архивировать предыдущий артефакт и снимок данных. Практически выполнить откат, а не только описать его.

Эксплуатационная модель должна отдельно учитывать:

- домен, статический хостинг/CDN и CI;
- хранение и исходящий трафик MEI, изображений/тайлов и архивов;
- резервные копии, возможную CMS, мониторинг и опциональный поисковый сервис;
- труд поддержки, обновление зависимостей, аудит данных и замену внешних интеграций.

Конкретные суммы считать после выяснения объёма файлов, посещаемости, институциональных ресурсов и редакционного инструмента; в этом плане тарифы не зафиксированы. Экономия базовой архитектуры достигается отсутствием постоянно работающего прикладного сервера и использованием уже существующих IIIF-ресурсов, когда это разрешено.

Резервировать код, научные исходники, нормализованные данные, права, MEI и релизные артефакты в независимом разрешённом хранилище; Git сам по себе не покрывает внешние файлы. По умолчанию: снимок при каждом выпуске, ежедневная копия изменяемой основной базы при её наличии и проверка восстановления не реже раза в квартал. Сроки хранения и целевые RPO/RTO утвердить с владельцем инфраструктуры.

Для долгосрочной сохранности подготовить архивный пакет релиза: данные, схемы, разрешённые MEI, описание прав, контрольные суммы, документацию и ссылку на код. Выбрать университетский или иной подходящий репозиторий; DOI, если требуется, выдаётся через подтверждённый институциональный процесс. Публикация архива не включает материалы, запрещённые к перераспространению.

## 15. Первые задачи при переходе к реализации

1. Назначить научного редактора, технического владельца и технического лида/ответственного за архитектуру; получить образцы данных, MEI, IIIF и описание существующего API.
2. Создать реестр прав и словарь Source–Witness–Work–Edition, выбрать пилот и зафиксировать язык интерфейса.
3. Согласовать UX-сценарии, содержание первого релиза и критерии научной приёмки.
4. Реализовать небольшой сквозной прототип: один реальный источник, несколько свидетельств, MEI с реконструкцией, IIIF, совместный просмотр и поиск по подготовленным метаданным; доступные данные DIAMM подключить только через подтверждённый разрешённый интерфейс либо внешние ссылки. Затем проверить репрезентативный пилот и размер индекса на полном доступном снимке метаданных.
5. По отчёту прототипа утвердить архитектурное решение, необходимость серверных компонентов, редакционный инструмент, стек, распределение ролей и уточнённую оценку работ/эксплуатации.
6. Перенести существующий визуальный концепт в утверждённую дизайн-систему и начать P3–P5.

Этот документ планирует реализацию. Он не подтверждает наличие прав, готовность полного корпуса, доступность API DIAMM или утверждение конкретного хостинга.

Ссылки проверены при подготовке плана 15 октября 2026 года. Они описывают возможности стандартов и инструментов; совместимость конкретного корпуса проверяется в P2.
